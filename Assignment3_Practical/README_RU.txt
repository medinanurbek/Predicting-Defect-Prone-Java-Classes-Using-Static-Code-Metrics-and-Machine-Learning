ЧТО УЖЕ СДЕЛАНО
Пять настоящих исходных CSV PROMISE получены из архива авторов Unified Bug
Dataset 1.2 (Zenodo, DOI 10.5281/zenodo.3693686). Выполнены очистка,
разделение по проектам, обучение Dummy, Logistic Regression, Random Forest,
XGBoost, сравнение 20 и 6 CK-метрик, оценка и permutation importance.
Это выполненный пилот. Полный nested leave-one-project-out benchmark,
несколько seed и проверка на новом внешнем проекте остаются планом.

КАК ЗАПУСТИТЬ В WINDOWS
Установите Python 3.12. В терминале откройте эту папку и выполните:
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe run_pipeline.py --output outputs_repeat

Исходные данные уже лежат в data. Для независимого повторного скачивания:
.\.venv\Scripts\python.exe fetch_data.py
Скачиваются только пять CSV из архива через HTTP Range. Весь архив размером
около 1 ГБ не нужен. Хеши пяти файлов проверяются перед обучением.

РЕАЛЬНЫЕ РЕЗУЛЬТАТЫ
Исходно 2 996 классов, после удаления совпадающих между частями векторов
метрик 2 954. Train: Ant/JEdit/POI — 1 679; validation: Ivy — 341;
test: Camel — 934. Обучение использует только train.
Удалены 11 validation и 31 test строка с совпадающими векторами.
Это консервативная защита: одинаковые метрики могут описывать разный код.
Удаление таких строк меняет состав оцениваемой выборки.

XGB20 выбран по validation average precision (0.4213) ДО оценки на test.
На test: precision 0.2984, recall 0.3048, F1 0.3016, ROC-AUC 0.5921,
AP 0.2582; TN=613, FP=134, FN=130, TP=57.
Dummy accuracy=0.7998 при recall=0. Это пример, почему одной accuracy мало.
LR6 имеет лучший наблюдавшийся test AP, но менять выбор модели по test
нельзя. Тест уже просмотрен, поэтому он не становится новым независимым
подтверждением после доработки моделей.

АНАЛИЗ ПРЕДЫДУЩИХ РАБОТ
1. Тема, RQ и цели согласованы: прогноз дефектности Java-классов на основе
   статических метрик и сравнение классификаторов. Их содержание сохранено.
2. В литературном обзоре нельзя утверждать, что CNN-LSTM превосходит RF
   или XGBoost, сравнивая проценты на разных датасетах и разбиениях.
   Результаты отдельных статей не образуют единую таблицу соревнования.
3. Feature selection, feature reduction и feature importance отвечают на
   разные вопросы. Разные выводы двух статей ещё не прямое противоречие,
   если различаются данные, алгоритмы, проверки и исследуемые процедуры.
4. JM1 не является прямым Java class-level аналогом выбранной задачи.
   Его результаты не стоит использовать как верхнюю границу точности.
5. Gap из литературного обзора шире принятого вопроса и целей:
   сравнение CNN-LSTM не обязательно для Assignment 3. Выбран выполнимый
   вариант LR/RF/XGBoost, CK6 против all20 и permutation importance.
6. В файле Assignment_2 внутри стоит заголовок Assignment 1. Это ошибка
   оформления; содержание относится к сформулированному вопросу и целям.

КАК ОБЪЯСНЯТЬ НА ЗАЩИТЕ ЗА 4–6 МИНУТ
До 1 минуты: вопрос, количественный вычислительный benchmark, единица
анализа — класс в одном релизе. Изучаем прогноз, причинность не доказываем.
До 2 минут: пять проектов, 20 метрик, bug>0 означает recorded defective.
Ноль — нет зарегистрированного дефекта, а не доказательство отсутствия багов.
До 3 минут: разделение по проектам, train-only imputation/scaling,
class weights, фиксированный порог 0.5. Почему не случайный split всех классов.
До 4 минут: показать запуск и metrics.csv; объяснить precision, recall,
F1, ROC-AUC, average precision и confusion matrix выбранной модели.
До 5 минут: показать 130 false negatives, слабый перенос и отличие
validation importance от доказанного универсального рейтинга метрик.
До 6 минут: planned leave-one-project-out, ограничение пяти старых проектов,
нужен новый внешний проект для независимого подтверждения после разработки.
